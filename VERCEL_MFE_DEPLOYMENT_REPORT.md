## 5. VERCEL DEPLOYMENT STRATEGY

### Deploy each MFE separately

- **Yes.** Deploy **three Vercel projects** (or three apps in a monorepo setup with separate root directories):
  1. **Core** (shell) — users hit this URL; it loads the shell and then remotes by URL.
  2. **Dashboard** — serves static assets and `assets/remoteEntry.js`.
  3. **OMS** — same.

### Which is the shell

- **Core** is the shell. Its deployment URL is the “app URL” users use. Dashboard and OMS URLs are only used as remote origins (for loading `remoteEntry.js` and for health checks).

### How remotes should be referenced (production)

- Remotes are referenced by **absolute production URLs** in Core:
  - Federation: `https://<dashboard-vercel-url>/assets/remoteEntry.js` and `https://<oms-vercel-url>/assets/remoteEntry.js`.

## 7. DEPLOYMENT BLOCKERS & FIXES

### Blocker 1: Core’s Tailwind `@source` paths — **FIXED**

- **Was:** `core/src/index.css` had `@source "../../dashboard/src"` and `@source "../../oms/src"`, which broke isolated builds.
- **Done:** Those lines are removed. Core owns all global styling. Contract: **if a remote needs a new utility, add it to Core first.** See `core/docs/REMOTE_STYLING_CONTRACT.md`.

---

### Blocker 2: `module.json` contains localhost — **FIXED**

- **Was:** `core/public/module.json` could be committed with localhost; production rule violated.
- **Done:** `module.json` is a **build artifact**. It is generated by `core/scripts/generate-module-json.js` before every `npm run dev` and `npm run build`. `core/public/module.json` is in `.gitignore`. Set `VITE_REMOTE_DASHBOARD_URL` and `VITE_REMOTE_OMS_URL` (and any new remotes) in deployment so the script writes production URLs. Main branch must never contain localhost in this file.

---

### Blocker 3: CORS

- **Risk:** Core (e.g. `https://core-xxx.vercel.app`) loads `https://dashboard-xxx.vercel.app/assets/remoteEntry.js` and may do HEAD/GET to dashboard/origin for health checks. Remotes must allow the Core origin (or `*` for assets).
- **Fix:** On Vercel, static assets are usually served without strict CORS by default. If you add custom headers or a server, ensure `Access-Control-Allow-Origin` includes the Core origin for:
  - `GET /assets/remoteEntry.js`
  - Optional: HEAD/GET to root or health endpoint for `checkModuleAvailable`.
- **Note:** `fetch(baseUrl)` in `useModules.ts` is to the remote origin; same-origin policy doesn’t block loading the script (cross-origin script is allowed), but the explicit fetch for “availability” is cross-origin and may need CORS if you enforce it.

---

### Blocker 4: Absolute imports (`@/`)

- **Status:** All apps use `@` → `./src` in `vite.config.ts` and tsconfig. Vite resolves these at build time; **no change needed** for Vercel.

---

### Blocker 5: Shared singleton (React)

- **Status:** Federation `shared` is set (react, react-dom, react-router-dom). Remotes use same major version (^19). React Compiler is disabled in remotes to avoid useMemoCache/singleton issues. **No change needed** if versions stay aligned.

---

### Blocker 6: Server-side / SSR

- **Status:** All three are client-only Vite SPAs (no SSR). No server-side Module Federation. **No action.**

---

### Blocker 7: assetPrefix / base path

- **Status:** No `base` or `assetPrefix` in config. Vercel serves from root of each deployment. If you later add a path prefix (e.g. `/app`), you’d set Vite `base: '/app/'` and ensure remote URLs in module.json include that base (e.g. `https://dashboard-xxx.vercel.app/app/assets/remoteEntry.js`). Not required for default deployment.

## 8. STEP-BY-STEP VERCEL DEPLOYMENT

1. **Create three Vercel projects** (or one repo, three projects with different Root Directories):
   - Project **core** → Root Directory: `core`.
   - Project **dashboard** → Root Directory: `dashboard`.
   - Project **oms** → Root Directory: `oms`.

2. **Deploy remotes first:** Deploy **dashboard** and **oms** so their production URLs are known. Copy those URLs for Core’s env.

3. **Configure Core project on Vercel:**
   - Build Command: `npm run build` (Core’s build script already runs `node scripts/generate-module-json.js` first).
   - Install Command: `npm install`
   - Output Directory: `dist`
   - Env vars: `VITE_REMOTE_DASHBOARD_URL`, `VITE_REMOTE_OMS_URL` (no trailing slash).

4. **Deploy Core** so the built Core uses the correct remote URLs from the generated `module.json`.

5. **CORS:** If any remote returns non-permissive CORS for its origin, fix headers so Core’s origin can fetch `remoteEntry.js` and the health-check request.

6. **Smoke test:** Open Core’s URL, confirm sidebar shows Dashboard and OMS, and that navigating to each loads the federated app without console errors.

  - **Single repo, three Vercel projects:** Keep `core/`, `dashboard/`, `oms/` as today. Each Vercel project points to its folder. No need for a root package.json unless you want shared tooling.

## 12. COMMON MISTAKES CHECKLIST

- [ ] **Deploying Core with localhost in `module.json`** → Use the generate script and set `VITE_REMOTE_*` env vars; `module.json` is gitignored and must never be committed with localhost in main.
- [ ] **Wrong Root Directory** on Vercel (e.g. leaving root blank when app is in `core/`) → install/build run in repo root and fail.
- [ ] **Output Directory** set to something other than `dist` for Vite → Vercel doesn’t serve the built app.
- [ ] **Building Core before remotes exist** → you don’t have production URLs for `module.json`; deploy remotes first or use placeholders and redeploy Core after.
- [ ] **CORS blocking** `remoteEntry.js` or health-check fetch from Core’s origin → fix headers on remote origins.
- [ ] **React version skew** between Core and remotes (e.g. Core 19, remotes 18) → risk of duplicate React or hooks errors; keep versions aligned and use federation `shared`.
- [ ] **Serving `module.json` with wrong baseUrl** (e.g. dev URLs in production) → double-check the file that’s actually in `core/dist` (or generated into `public`) after build.
- [ ] **Using `npm run dev:remote` as build command** on Vercel → that’s for local preview; use `npm run build` and Output Directory `dist`.

## 14. ARCHITECTURE IMPROVEMENTS (NEXT ITERATION)

Not blockers; they reduce pain as the system grows.

- **Split build-time vs runtime config:** Use `module.build.json` (for Vite) and `module.runtime.json` (served to browser) so runtime config can change (feature flags, rollout, hiding MFEs) without rebuilding. See `core/scripts/generate-module-json.js`; extend to emit two files when needed.
- **Remote contract (types):** Core has `core/src/types/remoteContract.d.ts` and `core/src/types/federation.d.ts`. When remotes grow, have each remote export a typed contract (e.g. `RemoteApp` with optional `mount`/`unmount`) so Core imports against it and avoids silent breaking changes.
- **Health endpoint:** Prefer remotes exposing `/health.json` with `{ "status": "ok", "version": "1.3.0" }` and Core checking that for availability (partial outages, canary). See `core/docs/HEALTH_ENDPOINT_CONTRACT.md`.
