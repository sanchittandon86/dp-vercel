# MFE POC — Microfrontend Proof of Concept
 
A monorepo containing three independent React + Vite microfrontend applications.
 
## Projects
 
| Project | Description | Path |
|---------|-------------|------|
| **Dashboard** | Dashboard microfrontend | [`dashboard/`](./dashboard) |
| **Core** | Core/shared microfrontend module | [`core/`](./core) |
| **OMS** | Order Management System microfrontend | [`oms/`](./oms) |
 
## Dynamic modules (Core)

The Core app reads **`core/public/module.json`** to build the navbar and routes. That file is **always generated at build time** (never commit it; see [Module config](#module-config-modulejson) below). Only MFEs that are **up and reachable** are shown in the sidebar and routable.

- **Dashboard** — Separate MFE; local `baseUrl` is `http://localhost:5175`, route `/dashboard`. Run with `cd dashboard && npm run dev:remote`. It appears in the navbar only when the dashboard app is up.
- **OMS** — `baseUrl` is `http://localhost:5174`, route `/oms`. Run with `cd oms && npm run dev:remote`. It appears in the navbar only when the OMS app is up.

For cross-origin health checks, MFEs may need to allow CORS from the Core origin.

### Module config (module.json)

`core/public/module.json` is a **build artifact**. It is generated by `core/scripts/generate-module-json.js` before every `npm run dev` and `npm run build` in Core. **Production rule:** main branch must never contain localhost in this file. Set `VITE_REMOTE_DASHBOARD_URL` and `VITE_REMOTE_OMS_URL` (and any future remotes) in your deployment environment so the script writes production URLs.

## Module Federation

Core loads OMS and Dashboard as **remotes** via `@originjs/vite-plugin-federation`. When you click Dashboard or OMS in the sidebar, the corresponding remote app is loaded and rendered in the same page (no iframe); React is shared so only one instance runs.

- **Federation needs built remotes:** Run Core with `npm run dev`; run Dashboard and OMS with `npm run dev:remote` (build + preview). Then open http://localhost:5173. **Run all three** for full experience: `core` (5173), `oms` (5174), `dashboard` (5175). Start remotes before or after core; the shell will load them when you navigate to their route.
- Remotes expose `./App` (via `remoteEntry.tsx`); the host lazy-loads `oms/App` and `dashboard/App`. Core derives federation remote URLs from `core/public/module.json` (baseUrl + `/assets/remoteEntry.js`). To add a new MFE, follow [How to add a new MFE](#how-to-add-a-new-mfe) below.

## Quick Start (Module Federation)

Install deps once per app, then run core + remotes:

```bash
# 1) Core (host)
cd core
npm install
npm run dev

# 2) Dashboard (remote) - build + preview so remoteEntry exists
cd ../dashboard
npm install
npm run dev:remote

# 3) OMS (remote) - build + preview so remoteEntry exists
cd ../oms
npm install
npm run dev:remote
```

## How to add a new MFE

1. **Create the remote app** (e.g. `apps/my-mfe/`) with Vite + React, Module Federation plugin, and an expose: `./App` → `./src/remoteEntry.tsx`. Use the same `shared` (react, react-dom) versions as Core. Do not ship Tailwind base/utilities in the expose chain; use only classes Core supports ([Remote Styling Contract](./core/docs/REMOTE_STYLING_CONTRACT.md)).

2. **Core – module config:** In `core/scripts/generate-module-json.js`, add a new entry to the `modules` array (id, path, label, icon, baseUrl). Add env var `VITE_REMOTE_MY_MFE_URL` and use it for `baseUrl` (fallback to `http://localhost:5176` or your chosen port). `module.json` is generated at build time; never edit it manually for environments.

3. **Core – federation:** In `core/src/components/FederationMFE.tsx`, add a lazy import (e.g. `const MyMfeApp = lazy(() => import('my-mfe/App'))`) and register it in `REMOTE_APPS` with the same key as the `id` in module.json.

4. **Core – types:** In `core/src/types/federation.d.ts`, add `declare module 'my-mfe/App' { ... }`.

5. **Core – sidebar:** In `core/src/components/app-sidebar.tsx`, add the new MFE’s icon to `ICON_MAP` (key = module `id`).

6. **Remote – build:** Ensure the remote’s Vite config outputs `remoteEntry.js` under `assets/` (see `dashboard` or `oms` for `rollupOptions.output.chunkFileNames`). Run Core’s build after the remote URL is set (or use the same port locally for dev).

7. **Health (optional, later):** Prefer the remote exposing `/health.json` and Core checking it for availability (see architecture notes in the deployment report).
